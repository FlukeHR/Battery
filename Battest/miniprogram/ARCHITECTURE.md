# 小程序整体架构

## 1. 技术选型

V0.1 推荐使用微信原生小程序 + TypeScript，不引入 React、Vue、Taro 或云开发。

原因：首版只服务微信端，页面数量少；原生方案运行链路短、包体小、平台能力适配直接，也能使用官方 TypeScript API 类型。若产品明确要同时发布支付宝、抖音或 H5，再切换为 Taro，并承担额外的跨端适配与测试成本。

## 2. 系统边界

```text
微信小程序
  ├─ 表单与本地校验
  ├─ 结果呈现与本地历史
  └─ wx.request
         ↓ HTTPS
battest.ccwu.cc
  └─ Next.js /api/predict
         ↓
  battery-prediction.ts
         ↓
  版本化 JSON 结果
```

小程序不保存算法副本，网站和小程序共享同一个服务端预测实现，从源头避免结果漂移。Python 训练管线仍属于离线研究系统，不进入小程序代码包。

## 4. 分层职责

- **pages/components**：只负责交互和展示，不拼接 API URL、不计算 SOH。
- **services**：统一超时、错误映射、响应解析和未来的 API 版本迁移。
- **types**：定义 `PredictionInput`、`PredictionResult` 与页面模型。
- **stores**：保存当前表单草稿和最近 20 份报告；不承担网络请求。
- **utils**：保持无副作用并可单元测试，禁止混入业务阈值。

## 5. 数据与状态

- 当前评估草稿保存在页面状态，离开流程时写入本机缓存。
- 成功结果生成本地 UUID，与输入快照、生成时间和算法版本一起保存。
- 仅保留 20 条；写入前验证结构，读取失败时隔离损坏记录。
- P0 不建立用户表、报告表或云端同步，因此无需微信登录。

## 6. 网络设计

- 基础地址通过非敏感配置区分开发与生产，生产固定使用 HTTPS。
- `wx.request` 统一封装 10 秒超时、一次性请求锁与错误码映射。
- 仅对连接失败提供用户触发的重试；不自动重试预测 POST。
- 发布前将 `https://battest.ccwu.cc` 配置为 request 合法域名并真机验证。
- 建议服务端增加 `request_id`、算法版本和轻量限流；日志不记录完整用户输入。

## 7. 安全与合规

- AppSecret 只能存在服务端，绝不写入小程序或仓库。
- 不申请位置、相册、手机号等 P0 不需要的权限。
- 若后续使用隐私相关接口，先更新隐私保护指引并在调用前取得同意。
- 报告避免“准确检测”“保证续航”等承诺，始终展示评估边界。
- 分享卡片不包含原始使用习惯或可识别个人的信息。

## 8. 测试策略

1. **单元测试**：字段校验、响应适配、风险展示、本地记录淘汰策略。
2. **契约测试**：固定输入请求网页 API，校验必需字段与枚举。
3. **组件测试**：步骤切换、提交锁、错误提示、删除确认。
4. **真机烟雾测试**：iOS/Android 各完成一次评估、分享和历史清理。
5. **回归测试**：服务端算法变更后，同一组样本在网页和小程序结果一致。

## 9. 实施阶段

- **阶段 A**：确认本 PRD 的 6 个开放决策，申请/确认 AppID 与域名条件。
- **阶段 B**：搭建原生 TypeScript 工程，实现 P0 页面和本地状态。
- **阶段 C**：增加版本化预测 API、契约测试与错误观测。
- **阶段 D**：目标用户内测、隐私与备案检查、提审发布。

## 模型整合说明

官网服务端读取 Python 导出的同一组 XGBoost 回归树：CALB 对应三元锂，HUST + MATR 对应磷酸铁锂。小程序仍只调用共用 API，不保存模型副本。新增来源与算法说明字段兼容历史响应；原始数据仅保留在本地。
